# Plan 14 | Foldkit UI v1: behavior once in core, parts, home screens, and a thin painter per Client

Status: Proposed. Revised after adversarial round 1 (U1-01 to U1-21). Scribe
issue #2568. The owner's words are in `user-messages/2026-11-20-ui-v1.md`.
Audit rounds and responses are in `adversarial/ui-v1-round-*.md`. The map of
what "complete" means past v1 is `14a-ui-coverage.md`.

Plan 04 (navigation) is Proposed, not decided. This plan builds a smaller
thing than plan 04's tabs and says where it differs.

## The rule

A part's behavior is written once, in Foldkit core, as a pure function with
no framework in it. A painter draws, and reports what happened.

"Behavior" is what a part does over time when a person uses it. Example: a
menu opens, the down arrow moves the highlight, Escape closes it. How the
menu looks is not behavior.

**The line between a rule and a painter's mechanics.** A rule is any number
with a unit of time, distance or count (500 ms, 10 px, 5 tries), or any
branch on what the person meant (a hold is not a press; a press that ends a
text selection is not a press). Rules live in core. Mechanics are how one
platform measures, scrolls, listens and draws. Example: "try again up to 5
times, 120 ms apart" is a rule and is in a painter today
(`packages/react-native/src/interaction/transcript.tsx:460`); "ask the list
to scroll to an offset" is mechanics.

**When the platform already holds the rule,** the painter reports the
outcome as one fact and core's timer rule does not run there. Example: React
Native recognizes a long press itself, so the phone tells `HeldLong()`, and
the 500 ms and 10 px belong to the platform on the phone. The web has no
recognizer, so it tells `PressedDown`, `MovedPointer`, `ReleasedPointer`,
and core decides. Which one a painter does is written in the part's
declaration, per painter, and tested.

## Words used here

Added to `glossary.md` in slice 3, before any code uses them.

| Word | Means | Example |
| ---- | ----- | ------- |
| Block | one small behavior: Schemas, `initial`, `step` | `longPress` |
| Part | a whole component: its blocks, its slots, its projection | a Transcript; a List with a row menu |
| Slot | one painted element of a part | a menu's row; a transcript's word |
| Fact | something that happened, told to a rule. A Message when the rule runs in `update`; a plain value when it runs in a runner. The glossary's present meaning (a Message a Command, Subscription or carrier produces) is the first case | `ScrolledByReader()` |
| Action | something a person or agent does on purpose to a part. Plain verb | `Open`, `HighlightNext` |
| Instruction | what a block's `step` asks for. The skill's use of "instructions" for the screen tree changes to "screen tree" | `BringToMiddle({ word: 'Spoken' })` |
| Port | what a runner needs from a painter. Same sense as AGENTS.md layer 4: a Service the core declares and an adapter fulfils. Not `foldkit/port` | `measure`, `wait` |
| Runner | the one shared loop that holds a painter-homed block's state and calls `step` | `TranscriptFollow.start(ports)` |
| Painter | what turns the screen tree into pixels for one Client | `paintReact` |

## The contract

### A block

```ts
type Block<State, Context, Fact, Instruction> = Readonly<{
  State: Schema<State>
  Fact: Schema<Fact>
  Instruction: Schema<Instruction>
  initial: State
  step: (
    state: State,
    context: Context,
    fact: Fact,
  ) => Readonly<{ state: State; instructions: ReadonlyArray<Instruction> }>
}>
```

- `step` never waits, never reads a clock, never touches a platform. Time
  arrives in `context.nowMs`. A timer is an instruction out
  (`WaitForLeaveCheck({ afterMs: 250 })`) and a fact back in
  (`ElapsedLeaveWait()`).
- State holds no sentinel. `TranscriptFollow.initial` uses
  `Number.NEGATIVE_INFINITY` for "nobody has scrolled" today; slice 3 makes
  both times `Option<number>`, so the State can be written as JSON.
- Items are data. A menu's order comes from its `items`, never from asking
  the page which element is next.

This is the one contract for a behavior. The sketch in
`skills/foldkit-screens/SKILL.md` (`ComponentMachine`, activities owned by
states) is replaced by it in slice 3. `Machine.define`
(`experimental/machine`) stays for a Program's own domain state charts, whose
edges return Commands: `examples/cardboard`. A block cannot use it, because a
block must also run where there are no Commands.

### Three homes for state

Asked in order, per block:

1. **Does anything painted, or anything an agent reads, depend on it?** If
   no, it is only memory of timing or measurement: **painter home**. The
   runner holds it. Example: the quiet second after a scroll.
2. **Should another device or the log see it?** If yes: **logged home**, in
   the Model, an ordinary Message. Example: which home screen is selected.
3. Otherwise: **device home**, in the Model, never logged. Example: Books'
   title menu, which is in the Model and local only "so a long press on a
   phone opens nothing on a desk" (`examples/books/core/src/program.ts:148`).

| Block | Home | Why |
| ----- | ---- | --- |
| `transcriptFollow` (timing memory) | painter | changes nothing painted |
| what the Program says about follow (`isFollowing`, off screen or not) | device | the Back to Playhead button is painted from it. Words has this today (`follow`, `playheadVisibility`) |
| `longPress` | painter | the timer only; its outcome is an Action on a part |
| `placement` | none | a pure function called while laying out, so the menu is never one frame late |
| `layers` (what is open, in what order) | device | painted; Books' menus are already here |
| `focusScope` (where focus returns) | painter | changes nothing painted |
| `liveClock` | painter | derived from the clock the Program gave; AGENTS.md: "do not add a Message per word" |
| `dragHold` | painter by default; device where the Program asks | Books' seek bar holds it in the painter. Words keeps `scrub` in its Model and paints the clock from it, and that stays |
| `fieldDraft` | painter | the phone and React keep the draft until submit; the Program hears on submit. See the note below |
| `listFilter` | device | it changes which rows are painted, so an agent must see it. It moves into the Model |
| `timedHint` (hints, key echo, copy feedback) | painter | timing of something the tree already declares |

Note on `fieldDraft`: unsubmitted text is painted, so by test 1 it belongs in
the Model. v1 leaves it in the painter and says so, because every keystroke
as a Message is the cost AGENTS.md warns about. A field whose text an agent
must read already has `token`, which sends each keystroke.

**How a device-homed or logged block joins a Program.** One composition
call, the way `ActionMenu.compose` already works
(`packages/foldkit/src/program/actionMenu.ts`): it adds the block's slice to
the Model, its facts and Actions to the Message union, and derives
`isLocalOnly`, `keepOnRefold` and `projectLocal` from the block's declared
home, so no Program lists them by hand. `ActionMenu` is the Model-homed
exemplar: its state is in the Model, its rows are a screen tree, and it is
painted today on HTML, React, the phone and both terminals with no painter
naming it. Slice 4 proves the new composition call on it before any new
block uses it.

**How a fact gets its time in `update`.** The Message carries it, stamped by
whoever sends it, as `MarkedMoment({ wallClockMs })` does today
(`examples/books/core/src/update.ts:1076`). `update` passes it to `step` as
`context.nowMs`.

**How an instruction reaches a painted slot from `update`.** Through a field
on the screen tree that carries a token, as `focusToken` does
(`packages/foldkit/src/renderers/types.ts:447`). A painter acts once per new
token value. A device-homed token is cleared on restore and never logged, so
it does not fire again on a refold or on another device. A timer is a
Command that sleeps and answers with the fact.

### A part

A part is what a painter hosts. It is declared once:

```ts
type Part = Readonly<{
  name: string
  blocks: Record<string, Block>
  slots: Record<SlotName, SlotDeclaration>
  actions: Record<ActionName, ActionDeclaration>
  project: (state, props) => Record<SlotName, SlotProps>
}>
```

- **A slot declares, as data:** its role (`menu`, `menuitem`, `tab`), how it
  takes focus (the highlight is state and focus stays on the container, as
  `@foldkit/ui` and the terminal already do; real focus does not rove), which
  gestures it listens for, and which fact or Action each gesture becomes.
  Core writes the ARIA from the role and the projected state.
- **Gestures are a closed list** every painter translates its platform's
  events into: `Pressed`, `PressedSecondary`, `HeldLong` or the raw three,
  `PressedKey(key)`, `ScrolledByPerson`, `ScrolledView`, `PressedOutside`,
  `PressedBack`, `DraggedTo(value)`, `Released`.
- **`project` is pure.** It returns, per slot, what a painter reads:
  `isCurrent`, `isExpanded`, `isDisabled`, `label`, `keys`. This is Zag's
  `connect` and the UI SDK's `attrs`, with Messages in place of handler
  closures.
- **Actions** are the part's verbs. Its keys and its agent tools are both
  derived from them.
- **Configuration** layers as base, then a named preset, then the call, with
  an unknown preset refused. Taken from foldkit-plus
  (`repos/foldkit-plus/packages/mixins-ui/src/configure.ts`).

A painter hosts any part through one generic host: bind each slot's
gestures, apply each slot's props, fulfil ports. It imports no part's rule.
Today's three painters import `TranscriptFollow` and choose which facts to
tell, and they choose differently: the HTML edge tells `ScrolledView` on a
scroll event and the phone never does. Slice 4 moves that choice into the
part's declaration.

**The test that can fail.** Per part and per painter: the same gesture by a
person gives the same facts. Example: a wheel turn over a Transcript gives
`ScrolledByReader()` on HTML, on React and on the phone's drag. It runs each
painter's real event binding with the platform event faked, not `step`.

**Ports are not designed here.** `TranscriptFollow` has five. A shared set is
extracted in slice 6, after `focusScope` and one device-homed block exist.
Nothing is claimed about its shape before then, except three requirements
already known: the runner is given `wait` (no block file names a timer),
`bringIntoView` answers whether it arrived (so the phone's retry becomes a
rule), and a press carries its value in a typed field, never joined into the
token.

## Atomic tiers

The skill's table, with two changes: an Organism is now defined as a Part,
and Navigation is added as a row above Screen. Template is unchanged.

| Tier | Is | Holds behavior? | Example |
| ---- | -- | --------------- | ------- |
| Atom | one node constructor | no | `Text`, `Button` |
| Molecule | a named pure `(model) -> UiNode` | no | Books' `tabsOf` |
| Organism | a Part | yes, through its blocks | a Transcript; a List with a row menu |
| Template | the device or host shell around a screen | no | `wrapDevice` |
| Screen | the whole tree for one destination | no | Books' `ProfilePage` |
| Navigation | which screens exist and where the person is | yes, in `update` | home screens, a stack, one modal |

## Navigation: home screens

v1 does not build plan 04's `Tabs = { active, stacks }`. No app here can
switch tabs from a deep page: Books shows its tabs on the library and the
profile only. v1 builds what Books needs and plan 04's kept stacks stay
Proposed.

**The change in core.** A Program may declare more than one root screen.
They are its **homes**. The stack's `root` holds the selected home.
`replacedRoot` and the `SetRoot` carrier instruction exist and are unused
(`packages/foldkit/src/navigation/structure.ts:292`, `:474`); `parseRoots`
already tries every root route (`uri.ts:412`). `Navigation.screens` takes
`homes: [first, ...rest]` beside `root`.

**Books, before and after.**

| | Before | After |
| - | ------ | ----- |
| Declaration | `ProfilePage` is `pushScreen`, allowed above the library | `ProfilePage` is a home |
| `ShowProfile` | `pages: [ProfilePage()]` | `replacedRoot(stack, ProfilePage())` |
| `ShowLibrary` | `pages: []` | `replacedRoot(stack, LibraryPage())` |
| `ShowReadAloud` | pushes the shelf above the library | the same. It is not a tab |
| `OpenPlayer` from Profile | sets library, title, player | the same: it selects Library, then title, player |
| Audible pages | above the library or the profile (`isHome`) | the same rule, unchanged |
| The Dock | drawn by the library and the profile pages | the same. No shell is declared in v1 |

**No address changes.** `/books`, `/books/profile`, `/books/audible`,
`/books/profile/audible`, `/books/<slug>/listen` print and parse as today.
`routesRoundTrip.test.ts` pins every one, and the 59 generated Expo route
files do not change.

**Messages and the log.** `ShowLibrary`, `ShowProfile` and `ShowReadAloud`
keep their tags, their Catalog entries and their category, so the terminal's
commands, the menu rows and every logged row stay valid. Each names where it
lands, so applying one twice, or on a mirrored device, lands on the same
screen. There is no `SelectedTab` Message and no "select again returns to
root" rule in v1.

**A stored stack from before.** A device Model saved with
`root: Library, pages: [Profile, ...rest]` is rewritten on restore to
`root: Profile, pages: rest`. One test.

**Back.** On a home that is not the first, Back goes to the first home, as
`NavigatedBack({ uri: '/books' })`. On the first home it leaves, as now. So
Android's back button, the browser's Back and the terminal's Escape all do
on Profile what they do today. The browser's history driver records a home
switch as a new entry; one test.

**The phone.**

- The homes share one carrier identity, so a switch is the same native
  screen with new contents: no push, no chevron, no swipe back from Profile,
  and the Dock does not slide because the screen it sits in does not move.
- **Cost, and the answer to it.** Today the library stays mounted under the
  pushed profile and keeps its scroll place. A plain root swap would unmount
  it and lose its place and anything a painter holds for it (a draft, the
  hold timer). So the phone's home screen keeps each home it has shown
  mounted and hides the ones not selected. The carrier plan gains the list
  of homes so the painter can ask for each one's tree. The web and the
  terminals repaint the selected home only, as they do today.
- Not checked: how the header title changes with no animation on Android.
  It is looked at on a device in the slice.

**What v1 takes from swift-navigation, plainly.** One tagged value for the
selected home, which is its rule that a place is one enum case and never a
set of booleans. Alerts as data (slice 7). ADR 0012 already took the rest: a
stack driven by a keyed diff, and a back gesture reported as a fact. v1 does
not replace React Navigation on the phone. See open decision 1.

## The agent surface

- A part declares Actions. They join the Program's Catalog through the same
  composition call, each marked as a UI Action, so `books actions --json`
  can list UI and domain Actions apart. The Catalog stays the one list an
  agent reads.
- This is already how Books works: `ShowTitleMenu`, `CloseTitleMenu`,
  `ShowWordMenu`, `CloseWordMenu`, `ExpandControls`, `CollapseControls`,
  `ShowSearch` and `CloseSearch` are Catalog Actions today. v1 marks them as
  UI Actions. It moves none.
- In v1 an agent can act on a part of its own Processor only. A
  device-homed part's Messages are never logged, so they reach no other
  device. Acting on another Client's part needs a directed request, which is
  not in v1.

**Reading another Client.** v1 publishes, per Processor, through the
existing `InstantProcessorPresence`
(`packages/instant/src/schema/schema.ts:418`): a device identity that
survives a relaunch, the host kind, the address it is on, whether it mirrors
navigation or keeps its own (`Mirror` or `SharedDomain`), and when. Never
the Model. A terminal lists them with `books where --all`.

Not in v1: asking another Client for its screen. It needs a rule for who may
ask (the same signed-in person only, enforced by Instant permissions and
tested), a projection that leaves out what a Program keeps home (Books'
Audible sign-in state is local "so a pasted sign-in address never leaves",
`program.ts:142`), and a change to Scribe's shared schema, which its owners
push.

## Keeping it true

The gate for every slice, run on the M5 since no hook or CI runs on this
branch: `pnpm lint`, `pnpm typecheck` for the packages touched, and their
`vitest` runs. A slice's commit message lists each command and its counts.

1. **The painter ratchet.** A checked-in file holds, per painter file, the
   count of timers (`setTimeout`, `setInterval`, `requestAnimationFrame`),
   held state (`useState`, `useRef`, module or closure `let`), listeners, and
   constants named with a unit (`Ms`, `Px`). A test fails when any count
   rises. A slice must lower the counts of what it replaces. This is the
   guard against the failure that started this plan: a rule added to a
   painter. Painters covered: `htmlEdge.ts`, `html.ts`, `paintReact.tsx`,
   `packages/react-native/src/interaction/*`, `packages/svelte/src/**`,
   `packages/opentui/src/**`, and `examples/words/foldkit/src/mount.ts`.
2. **Core stays clean.** `packages/foldkit/src/behavior/**` may not import
   `foldkit/html`, React or React Native, by any path including the `foldkit`
   root barrel's `Html`, `Mount`, `Dom`, `Render`, `File`; and may not name
   `document`, `window` or a timer. `transcriptFollow.ts` calls `setTimeout`
   today (`:343`), so slice 3 gives its runner a `wait` port and moves it to
   `behavior/`, and the rule is on from that commit.
3. **`@foldkit/ui` may not grow its DOM use.** The same ratchet, counting
   its imports of `foldkit/html`, `foldkit/dom`, `foldkit/mount`,
   `foldkit/render`, `foldkit/file`, `@floating-ui/dom` and its uses of
   `document` and `window`, per file. `internal/` leaves the lint's ignore
   list. Whether the counts are driven to zero is open decision 2.
4. **A short `AGENTS.md` beside each painter** and in `packages/ui`, naming
   the rule, the ratchet, and `TranscriptFollow`.
5. **A block is done when every copy it replaces is deleted** in the
   painters v1 covers, and the ratchet's counts show it.

## Open decisions for the owner

1. **The phone's carrier.** ADR 0012 (Accepted) names React Navigation and
   Expo Router. On 2026-11-20 he said: "i'm not a huge fan of react
   navigation personally i think it it's way too heavy-handed". The carrier
   loop is already ours and already diffs by key. What React Navigation
   supplies is the native stack view, the header, the edge swipe, and Expo
   Router's linking and its 59 route files. Replacing it means rebuilding
   those four on `react-native-screens`. Proposed: v1 does not, and the
   replacement gets its own plan after slice 1 shows what the phone still
   gets wrong.
2. **`@foldkit/ui`.** He said: "let's create linters for packages UI that
   make them JavaScript framework agnostic and only use core fold kit
   primitives etc and then get rid of the fold kit HTML", and also "make our
   library complete and at the core". Its widgets hand the caller `Html`
   (`Tabs` takes `toView: (render) => Html`), so removing `foldkit/html`
   from it changes the API that 31 examples, the website and devtools call.
   Two ways:
   - **(a) Proposed.** The rule for each widget moves to a core part. The
     `@foldkit/ui` widget keeps its API and becomes the HTML painter's view
     of that part. Its DOM counts fall as Commands and Mounts become ports,
     and nothing that imports it breaks.
   - **(b)** Its views are redrawn as screen trees and the `Html` API goes.
     Every importer is rewritten.
3. **Should Words and Books follow the voice the same way?** After slice 2
   they share one rule with two settings. Words moves by section and stops
   the moment you scroll. Books moves by word and stops once the word leaves
   the middle. Proposed: leave both as they are until he has used both.
4. **One Action list or two.** He said: "I don't like associating the like
   what what component ha what agent actions are listed in every component
   we want to make sure that those are UI related and not domain related
   Yeah, our catalog already does this". Read here as: keep one Catalog, and
   mark each Action as UI or domain. The other reading is that parts should
   list no Actions at all.
