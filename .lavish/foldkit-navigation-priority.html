Foldkit architecture exploration

Navigation is state. The host makes it visible.

Start with the existing multiple-counters example, lift it into a renderer-free Program, add one nested navigation domain, and prove replay plus deep linking before adding mobile or file-based router adapters.

Recommendation: multiple counters is the right first vertical slice.

The useful pieces already exist

This is not a greenfield navigation project. Foldkit already has the three seams that need to be joined, plus one intentionally missing seam.

Existing example

Identified Counter Submodels

examples/counters already adds and removes rows, keys them by stable IDs, and lifts child Messages through GotCounterMessage to the correct row.

Existing runtime

Renderer-free Program and replay

The Program prototype owns Schema Model, Message, update, Commands, journal, replay, and portable state and tape routes without assuming a view framework.

Existing type tools

Nested Schema unions

Effect 4 provides Schema.TaggedStruct, Schema.TaggedUnion, nested Schema.Union, exhaustive matching, and Schema-backed constructors.

The boundary to build

The domain owns the destination. A pure projection derives a host target. The adapter reconciles the real navigator and converts external navigation events back into Messages.

First domain shape

Use nested tagged unions to eliminate mutually invalid presentation states. Keep the Counter collection authoritative and treat destination-to-entity membership as a checked runtime invariant. 

Model {
  counters: Array<CounterRow>
  navigation: Navigation
}

Navigation =
  | CounterList
  | CounterDetail {
      counterId: CounterId
      destination: Option<DetailDestination>
    }

DetailDestination =
  | CounterFactAlert { fact: string }
  | DeleteCounterConfirmation

Message =
  | ClickedAddCounter
  | CreatedCounter { counter }
  | GotCounterMessage { id, message }
  | SelectedCounter { id }
  | DismissedCounterDetail
  | OpenedDeepLink { route }
  | ...
Compile-time win List and detail cannot both be active. A fact alert and delete confirmation cannot both be active.
Identity rule Every child Message carries a stable Counter ID. Never route a child Message by an array position.
Relational limit TypeScript cannot prove that a runtime ID belongs to a runtime collection. The update and route boundary must validate that relationship.
Replay rule Fact results and generated IDs arrive as recorded Messages. Historical update discards returned Commands.

Recommended build order

Each stage answers one architectural question. Later stages consume the contracts proven by earlier stages instead of changing their meaning.

Use inventory and drafts to pressure-test sync and permissions. Add ledger and transfer semantics only after the authority model is proven.

Adapter order is about learning value

Do not start with a universal router API. Start with the easiest host that can falsify the contract, then move toward hosts with stronger build-time and gesture constraints.

1

Headless simulator

Proves state transitions, target projection, reconciliation, and replay without framework noise.

2

Browser History

Builds on Foldkit’s existing URL Messages and navigation Commands, while exposing two-source-of-truth mistakes quickly.

3

React Navigation

Exercises nested stack, tab, drawer, native back, and gesture dismissal. Its navigation object is host state, so reconciliation must be careful.

4

Expo Router

Its route graph is derived from src/app. Generate or audit thin route shells, then drive runtime destinations through Expo Router’s own typed URL API.

5

React Router

Map the same parser-printer and navigation target into a code-declared web router after the URL contract is stable.

6

Next.js App Router

Keep file-system pages and server boundaries as thin framework shells around the same client Program and domain routes.

Do not start with scaffolding. A generator can create Expo or Next route shells later, but generating files before the state and reconciliation contract exists will freeze accidental framework details into the public API.

Keep four boundaries separate

The brainstorm spans navigation, sync, sharing, and authority. They can share protocols, but they must not collapse into one mechanism.

Boundary What it means What it must not imply
Identity Who is making the request or running the processor. That the identity may read or mutate a record.
Entity sharing An owner grants a user or capability read or write access to a live entity. That a replay tape containing that entity is safe to publish.
Tape sharing An immutable, derived artifact is exported under an explicit privacy policy. That post-capture PII scanning alone makes arbitrary Messages safe.
Trusted effect A processor with privileged Resources validates intent and performs an authoritative operation. That an untrusted client may emit a success fact or mutate authoritative state directly.

Three guardrails

These are the places where an appealing abstraction can quietly violate replay, authorization, or Elm Architecture.

Modeling

Do not promise impossible relational proofs

A union can forbid simultaneous destinations. It cannot prove that a decoded Counter ID is present in a runtime collection. Validate at boundaries and preserve the invariant in update.

Replay

Do not record host operations as truth

Record Messages and Models. Derive navigation again for the selected frame. Replaying push and dismiss operations would duplicate side effects and diverge after a seek.

Security

Do not equate shared code with shared authority

The same Program protocol can run everywhere. Credentials, authorization checks, authoritative storage, and privileged Resources belong only on trusted processors.

The first slice is done when

These checks turn the multiple-counters example into an executable navigation contract, not just a UI demo.

A child Message and fact Command result always return to the Counter with the matching stable ID.
Compile-time fixtures reject simultaneous incompatible destinations and incomplete destination mappings.
Direct links parse into typed navigation Messages, and every valid destination prints a canonical route.
Back, forward, and dismissal update the Program through Messages without feedback loops.
Replay seek shows the correct screen and presentation without executing historical Commands.
A live branch from a settled frame synchronizes once, then new navigation and fact Commands execute normally.
