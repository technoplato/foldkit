InstantDB shared Programs

Messages travel. Effects find a Processor.

Synchronize immutable facts, derive the Model everywhere, and place side effects according to capability. A Client remains a runnable adapter. A Processor is one live Program occurrence.

Proposed invariant

The Message history is authoritative. Model snapshots are disposable local checkpoints, never shared domain truth.

Keep the nouns separate.

This resolves the ambiguity in “one app on one device.” One Client can host several Processors. A headless Client can host Processors without presenting any human interface.

Program

Portable Model, Message, update, Commands, lifecycle definitions, routes, versions, and migrations.

Client

One complete runnable adapter. It owns interaction, renderer, platform Layers, URI carrier, and launch behavior.

Processor

One running Program occurrence. It consumes Messages and advertises the capabilities its Layers can perform.

Host

The composition and lifecycle owner that launches, finds, and supervises Clients and Processors.

The durable effect loop.

A Foldkit Command is currently an executable local Effect closure. It is not a network payload. Durable or movable work gains a separate versioned request contract.

1 · Requested fact ClickedScanCheck joins the Message tape.
2 · Local update Every Processor derives the same next Model and effect manifest.
3 · Effect request The manifest yields capability, policy, and idempotency data.
4 · Capable Processor The selected Processor runs its local Effect. Others keep it inert.
5 · Result fact SucceededCaptureCheck rejoins the tape.
Required runtime seam

Today every ProgramRuntime executes every Command returned by update. Shared Program mode needs a scheduler interception point and a Schema-defined effect manifest. An opaque Effect closure cannot be serialized or reverse-engineered into a durable request.

Delivery is at least once with authority-side idempotency. Duplicate occurrence IDs are rejected before journal admission. If a stale result is accepted, every Processor applies it and update deterministically leaves the Model unchanged.

Four data boundaries.

Provenance matters, but not all provenance belongs inside the domain Message. Keep delivery mechanics from becoming a second hidden input to update.

Domain Message

Only facts update needs.

  • Past-tense event and payload
  • Entity, session, and request IDs
  • Sanitized success or failure
  • Semantic origin only when behavior changes

Transport envelope

Ordering, authentication, audit, and delivery provenance.

  • Occurrence, actor, origin Client, device installation, ingress Processor, and session IDs
  • Program, event, and envelope versions
  • Causation, sequence, timestamps, digests
  • Auth, signature, attempt, lease, and trace data

Durable effect request

A movable, survivable request derived from an effect manifest.

  • Effect and request format versions
  • Stable request ID and idempotency key
  • Capability, affinity, and unavailable policy
  • Public arguments or content addresses

Processor Layer

The Client Host supplies it. Live handles and secrets stay local.

  • Private keys and provider credentials
  • Camera and microphone handles
  • Filesystem bookmarks and refresh tokens
  • Raw protected material behind opaque grants

Placement is capability-driven.

Authentication decides whether a Message is admitted. Placement decides which capable Processor performs its resulting effect. Renderer and device brand are not authorization lists.

Use each Instant primitive for one job.

Durable facts and ephemeral coordination have different failure semantics. Keeping them separate protects offline convergence.

Entities + live queries

Durable Message occurrences, membership, effect requests, results, revocation, and materialized projection checkpoints.

Rooms + presence

Connected Processor identity, liveness, roles, capabilities, protocol ranges, and last-applied positions. Product-visible availability still enters the Model through accepted Messages.

Topics

Transient hints and cursors only. Never the only copy of a Message or effect request.

Streams

Resumable media and artifact bytes, linked from a durable Message or result. Not the structured multi-writer journal.

A terminal can leave the Processor running.

Snapshot-based terminal interaction does not require snapshot-based execution. Timers, microphone capture, and other long-lived sources belong to Subscriptions or ManagedResources owned by a headless Processor.

1

One-shot terminal Client connects It does not create or own the long-lived scope.

2

Client sends a canonical Message The Processor runs finite Commands and keeps lifecycle sources active.

3

Client prints the current Model It may observe intermediate Models before choosing its snapshot.

4

Client disconnects The Processor survives with zero connected Clients.

Lifecycle placement is separate

Shared timers, microphone Subscriptions, and ManagedResources also need capability, affinity, cardinality, a durable lease or fencing token, takeover, release, and reconnect rules. Otherwise every Processor can acquire the same source or emit duplicate Messages.

Recommended design order.

Settle semantics before choosing the final Instant schema. This gives us a small vertical proof with falsifiable behavior.

1

Placement algebra

Settle cardinality, capability, affinity, and unavailable behavior.

2

Message envelope

Separate semantic provenance from transport and audit provenance.

3

Ordering + offline proposals

Define admission, conflicts, actor sequence, and explicit incompatibility.

4

Pairing + capabilities

Define QR grants, guest scope, expiry, revocation, and negotiation.

5

Effect lifecycle

Define claiming, leases, retries, cancellation, and terminal results.

6

Narrow observable proof

Prove one remote-control flow before building the full Instant adapter.

Decision 01

Should a distributed Command support Every?

My recommendation is to start with One. Effects that merely change presentation on every Client remain local Client behavior. Add Every only when each execution and each outcome must be durable Program truth.
