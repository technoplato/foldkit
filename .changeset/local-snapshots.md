`Runtime.start` and `Runtime.startHandle` take a `localSnapshot` store, so each device keeps its own state: up to four snapshots of its fold, the rows after the oldest, and the engine cursor. A reload paints the newest snapshot at once, asks the engine only for rows it received after the cursor, and folds them onto the newest snapshot that covers them, so a row that landed late refolds from the snapshot just before it; only a row older than every kept snapshot reads the whole log again. Old rows are never replayed as live Messages. Snapshots are spaced 200 rows apart and pruned past four. A snapshot holds only what every Processor sees and only rows the engine confirmed, so tabs can share one store and a write that never lands is never kept. It is the Program's own Model, encoded with its Schema and stamped with its id and version; state from another version is dropped and rebuilt from the log. Build a store with `Runtime.LocalSnapshot.webStorage(localStorage, key)`, `Runtime.LocalSnapshot.fromPromises({ load, save })` for AsyncStorage, or `localSnapshotFile(localSnapshotPath(name))` from `foldkit/cli` on Node and Bun. `SyncEngine` gains an optional `readSince(cursor)`, and `Runtime.Memory` implements it.

Every row the runtime writes carries `programVersion`. `@foldkit/instant` adds the optional attribute to the message entity, reads rows after a cursor in the order Instant received them (`readSince`), and follows only the newest 100 rows live (`subscribeRecent`), so a Counter reload downloads 73 KB instead of about 1.5 MB.
